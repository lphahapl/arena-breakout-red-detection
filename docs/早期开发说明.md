# 暗区突围红品检测 v0.2.0 / v0.3.0

目前提供 Python 便携版 v0.2.1 和 Rust 原生版 v0.3.1。两版启动自动检测中文 OCR，缺少时请求 Windows 管理员授权安装系统组件，界面显示状态及重试入口。Python 版内置运行时及调用库；原生版无需安装 Python、Rust 或 OpenCV。桌面导出目录附有使用说明和验证报告。

选择游戏窗口、检查预览后开始检测，随后让游戏搜索面板保持可见。默认只扫描窗口右侧 40%，可在 `settings.json` 的 `work_region` 指定 `[x,y,w,h]` 比例。选定窗口不存在时显示错误，窗口被遮挡时暂停检测并保留未完成记录。

网页的“运行历史”入口显示每次运行的起止时间、时长、完整结算数、出红率、未完成数、截图及人工复核。出红率按“有红品的完整保险箱次数 ÷ 完整结算保险箱次数”计算，覆盖所有红色稀有度物品，每次完整打开计一次，暂不去重。人工复核保留为独立标签，不覆盖原始判定。

v0.2.0 双击 `启动.bat`，数据位于 `app/runs`，默认本机端口 17833。v0.3.0 双击 `暗区红品检测.exe`，数据位于 `runs`，默认端口 17933；使用网页“退出程序”按钮结束后台程序，关闭网页会保留后台运行。端口冲突时以实际打开的地址为准。

原生代码与构建说明见 [native/README.md](native/README.md)，具体验证结果见 [验证报告.md](验证报告.md)。下文保留 Python 开发工具与早期诊断说明，发行版请以附带使用说明为准。

# Python 开发工具

纯屏幕采集，不注入、不 hook、不读游戏内存。原理上等同于 OBS 截图。

## 安装

```bash
python -m pip install mss
```

numpy / opencv-python 已有（本机 numpy 2.3.4 / cv2 4.13.0）。

**只用路线二的安全箱监控和路线一，装 `mss` 就够了。** 只有容器名字 OCR
需要额外的 WinRT 包（见下面「数出摸了几个保险箱」一节）。

## 快速开始（推荐）

双击 **`start.bat`**。浏览器会自动打开 <http://127.0.0.1:17833/>，然后在网页里：

1. 右上角下拉选游戏窗口（实测标题是 **`暗区突围：无限`**）
2. 点 **开始检测**
3. 切回游戏

或者双击 **`start-phone.bat`** —— 绑 `0.0.0.0` 并打印一个局域网地址，
用手机浏览器打开。**这样浏览器完全不占游戏屏幕**，是最省心的用法。

> ⚠️ **一个必须知道的限制**：截图走的是桌面合成，**浏览器窗口盖住游戏时，
> 抓到的就是浏览器**。所以要么用手机 / 第二块屏，要么让游戏保持在最前。
> 程序里做了前台检测：游戏不在前台就喂空帧，让状态机走 miss 结束会话，
> 不会记录错的数据——但也就等于那段时间不检测。

## 两条路线

| | **路线一**：检测容器搜索面板 | **路线二**：只盯安全箱 |
|---|---|---|
| 命令 | `snap` / `watch` | `select-box` / `box` |
| ROI | 整屏右 40%，干扰多 | 几百像素，位置固定 |
| 要检测 UI 吗 | 要，还要区分容器/背包/地图 | 不要 |
| 场景纹理误报 | 有（枪皮花纹、地砖、格栅） | 基本没有 |
| 判断的是 | 这个容器里有没有红 | 你是不是**刚拿到**一个红 |

路线二明显更稳，推荐优先用它。红品检测器（第 3 层）两条路线共用。

## 用法

```bash
# Web UI（等价于双击 start.bat）
python main.py serve                     # 起服务并自动开浏览器
python main.py serve --host 0.0.0.0      # 绑局域网，手机也能看
python main.py serve --port 20000 --no-browser

python main.py list                     # 列出窗口，找游戏窗口标题

# 完整链路（无 UI 的命令行版）
python main.py --window 暗区 track        # OCR 认保险箱 + 网格确认 + 色块检测
python main.py --window 暗区 track -v     # 每轮都打印，调参时用

# 容器名字 OCR 诊断（先跑这个确认关键词）
python main.py --window 暗区 name         # 打开目标容器面板，看 OCR 读出什么

# 路线二（安全箱）
python main.py --window 暗区 select-box  # 交互式框选安全箱，只需做一次
python main.py --window 暗区 box         # 只监控安全箱，报「新增红品」

# 路线一
python main.py snap                     # 抓一帧分析，全部中间图存到 debug/
python main.py watch --fps 2            # 持续跑，检测到面板/红品时打印
python main.py --monitor snap           # 不找窗口，直接抓主显示器
```

## Web UI

`webui.py` + `runner.py`。标准库的 `ThreadingHTTPServer`，没引额外依赖。
后端仍是 Python（要抓屏和跑 OCR），浏览器只做展示。

| 路由 | 用途 |
|---|---|
| `GET /` | 页面 |
| `GET /api/status` | 运行状态、连续未出红数、当前会话、OCR 耗时 |
| `GET /api/events?since=N&run=X` | 增量拉事件（`since` 是上次的 `last_seq`） |
| `GET /api/windows` | 列出可见窗口供选择 |
| `POST /api/window` | 设置目标窗口（运行中不允许改） |
| `POST /api/start` / `POST /api/stop` | 控制 |
| `GET /shot/<run>/<file>` | 截图（做了路径穿越防护） |

**窗口在网页里选**，不是命令行传——这样 `start.bat` 不用带中文参数，
绕开了 cmd.exe 解析 .bat 时的代码页乱码问题。

### 记录的内容

每次检测成功都会存进 `runs/<时间戳>/`：

```
runs/20260926_024819/
  events.jsonl                 每行一个事件
  0001_panel.png               开箱时的面板截图
  0002_panel.png               无红结算
  0003_panel.png               出红结算
  0003_red_annotated.png       出红：命中的色块被框出来
```

`events.jsonl` 每行：

```json
{"seq":3,"t":"2026-09-26T02:50:11","kind":"red","text":"保险箱",
 "cells":[4.0,4.0],"period":[91,91],"rect":[263,180,378,382],
 "observations":6,"red_count":1,"streak":0,
 "shots":["0003_panel.png","0003_red_annotated.png"]}
```

`kind` 三选一：`start`（开箱）/ `clean`（无红）/ `red`（出红）。
截图在每个事件都存，出红额外存一张带标注框的。

### 页面

- 顶部大数字：**当前连续未出红**、已结算保险箱数、出红次数、OCR 平均耗时
- 进行中会话卡片：当前容器名、格子尺寸、已观察轮数、是否已见红
- 检测记录时间线：时间、徽章（出红/无红/开箱）、缩略图，点图放大
- 右上角可切换查看**历史 run**

## 性能：OCR 是唯一的大头

实测（2560x1440，本机）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| **OCR（右 0.4 全量 1024x1440）** | **131~144 ms** | **76%** |
| `find_grid` 网格检测 | 35 ms | 20% |
| `find_red_blobs` 色块检测 | 7 ms | 4% |

**OCR 占了整链路的四分之三。** 更糟的是早期实现每轮都调它——
0.5s 帧率下单核 **20.5% 常驻**，屏幕上根本没 UI 的时候也一样。

### 改法一：OCR 单独限频（已实现）

OCR 的频率和帧率解耦。面板开着要好几秒，1 秒查一次足够：

```bash
python main.py --window 暗区 track --ocr-interval 1.0   # 默认
python main.py --window 暗区 track --ocr-interval 2.0   # 更省
python main.py --window 暗区 track --ocr-interval 0     # 每轮都跑，调参时用
```

`--ocr-interval` 同样适用于 `serve`。

实测占空比（真实等待，非估算）：

| 配置 | IDLE 占空比 |
|---|---|
| 每轮都 OCR（改之前） | **20.5%** |
| OCR 限频 1.0s（现在的默认） | **11.4%** |
| OCR 限频 2.0s | 6.5% |
| SESSION 阶段（面板开着，只跑网格+色块） | 5.1% |

会话结算后会立刻允许下一次 OCR（`_last_ocr_t` 归零），
不会刚关完箱子还要白等一个限频周期。`test_track.py` 有专门用例覆盖这点。

### 改法二：把 OCR 区域裁到名字那一小块（最大的杠杆，待数据）

**注意：不能用缩放省时间。** 实测把右 0.4 缩小后再 OCR：

| 输入 | 耗时 | 识别行数 |
|---|---|---|
| 1024x1440 原尺寸 | 131 ms | 20 |
| 缩到 75% | 103 ms | 14 |
| 缩到 50% | 55 ms | **5** |
| 缩到 35% | 33 ms | 3 |

缩放会直接丢字（20 行 → 5 行）。但**裁剪不改变文字大小，精度不掉**：

| 输入 | 耗时 | 识别行数 |
|---|---|---|
| 右 0.4 全量 1024x1440 | 143.6 ms | 20 |
| 名字区 190x70 | **9.0 ms** | 2 |

**15.9 倍差距。** 投影到 IDLE 占空比：14.4% → **0.9%**。

用法：

```bash
python main.py --window 暗区 track --ocr-region 812,1000,247,85
```

跑一次 `name` 命令，它会**直接打印出可粘贴的 `--ocr-region` 值**
（`test_ocr.py` 里有偏移正确性的回归用例，实测和真值精确一致）。

#### 裁剪留白必须给够（否则 0 命中）

这是实现时实测撞到的坑：**Windows OCR 的行检测需要文字周围有足够空白**，
裁太紧会直接识别不到，不是识别错而是**完全返回空**。

文字高 15px 的标签，实测：

| 上下留白 | 结果 |
|---|---|
| 0px | 0 行 |
| 8px | 0 行 |
| 15px | 0 行 |
| **25px** | 命中 |
| 30px | 命中 2 行 |

所以留白要**按文字高度算**，不能用固定小值。`name` 命令用的公式是
`pad_x = max(100, 文字宽)`、`pad_y = max(35, 文字高 × 2.5)`。

附带发现：裁剪不仅更快，**bbox 也更准**。同一张图，全图 OCR 给出的
位置偏了 20px（大片纯色背景上定位不准），裁剪版精确命中真值。

> ⚠️ 另一个相关坑：**不能用缩放代替裁剪**。缩放不改变留白比例但也缩小了
> 文字，实测缩到 50% 识别行数从 20 掉到 5。裁剪不改变文字大小，精度不掉。

## 完整链路：`track`

回答最初那个问题——「连续摸了多少个保险箱没出红」。

### 链路：OCR 锚定，没有网格检测

```bash
python main.py --window 暗区 track
```

```
1. OCR 工作区，找容器名字（关键词「保险箱」）
2. 命中 -> 用名字的 bbox 锚定面板，进入会话
3. 会话里：小区域 OCR 确认名字还在 + 全区域色块检测找红品（latch）
4. 名字连续 N 轮消失 -> 结算：有红 streak 归零，没红 streak += 1
```

### ⚠️ 原来的「网格检测」层已被拿掉

初版设计里有一层「大量重复格子 = UI 出现」的判据（边缘密度 → 连通域 →
自相关测格子间距）。**拿真实截图实测后这条被删了**，三个原因：

1. **容器面板格子很少**。实测「电子保险箱」面板是 **2×2、间距约 87px**——
   格子太少、投影太短，自相关根本形不成显著峰。
2. **物品图案纹理淹没信号**。那一格装着「集邮册」，图案细节极丰富，
   边缘投影被内容边缘主导，周期性被压掉。实测 `find_grid` 直接返回
   `没测出规则格子`。
3. 它本来只是**弱判据**：枪皮花纹、地砖、天花板格栅都会误命中（实测撞到过）。

而 OCR 是强判据，还顺带给出容器名字的**精确 bbox**（实测 `(37, 161, 105, 21)`），
直接用它锚定面板就够了。少一层，还更快。

> `detect.find_grid` 保留着，`snap` / `watch` 诊断命令还在用。
> 但 `track` 这条主链路已经不依赖它。

### 自适应 OCR 区域

第一次 OCR 要扫整个工作区（实测 **300ms** —— 游戏画面里还有 HUD、物品名
要一起识别）。拿到名字 bbox 之后就只扫名字周围那一小块（**~9ms**）。

```
IDLE      oos_interval      = 1.0s   全区域 300ms
已锚定    ocr_interval_fast = 0.2s   小区域   9ms
```

**自愈**：IDLE 里连续 2 次没命中就清掉锚点，退回全区域重找——
否则锚点过期（换了容器类型、名字位置变了）会一直用失效的小区域扫，
永远找不到也永远不重试。

### 一个实测确认过的陷阱：容器名字标签本身就是红的

实测「电子保险箱」这个名字标签是**红底**，而且会通过 R/G、R/B 判定：

| 采样点 | hex | R/G | R/B | 判定 |
|---|---|---|---|---|
| 标签右侧底 | `#4D1D1A` | 2.66 | 2.96 | 会过 |
| 标签上边框 | `#341716` | 2.26 | 2.36 | 会过 |
| 真红品基准 | `#331410` | 2.55 | 3.19 | — |

`#341716` 和 `#331410` 几乎一模一样（R 52 vs 51、G 23 vs 20、B 22 vs 16，
全在容差内）。

**好在不需要为它做特殊处理**——核心匹配率把两者分开了：标签底色的实测
`core_match` 只有 **0.005**（真红品是 **0.831**），而那条 `#341716` 只有
1~2px 宽，腐蚀后没有核心像素。

⚠️ 所以**别把 `red_core_match_min` 调松**，它是这里唯一的防线。
`test_real.py` 里有专门的用例盯着这件事。

附带发现：裁剪不仅更快，**bbox 也更准**。同一张图，全图 OCR 给出的
位置偏了 20px（大片纯色背景上定位不准），裁剪版精确命中真值。

> ⚠️ 另一个相关坑：**不能用缩放代替裁剪**。缩放不改变留白比例但也缩小了
> 文字，实测缩到 50% 识别行数从 20 掉到 5。裁剪不改变文字大小，精度不掉。

## 完整链路：`track`

回答最初那个问题——「连续摸了多少个保险箱没出红」。

### 级联顺序：OCR 在前，网格在后

两个判据强弱差很多：

| | 误报情况 | 开销 |
|---|---|---|
| 网格检测（大量重复格子） | **弱**：枪皮花纹、地砖、天花板格栅都会命中（实测撞到过） | ~35ms |
| OCR「保险箱」 | **强**：场景纹理几乎不可能凭空拼出这三个字 | ~126ms |

**把弱判据放前面，每次误报都要白跑一次 126ms 的 OCR**，按实测误报率这个浪费很大。
反过来极少误报，偶尔误报一次再让网格否掉，成本可忽略。

但**网格不能省**——色块检测必须知道面板矩形在哪，而只有网格检测能给这个矩形。
两者不是二选一，是顺序问题：

```
每轮:
  1. OCR 右 0.4，找「保险箱」        ~126ms   ← 强闸门
  2. 命中 -> 网格检测确认 + 定位面板   ~35ms    ← 弱确认，但提供面板矩形
  3. 面板内色块检测                          ← 复用第 3 层
```

### 会话式

搜刮要好几秒，而且**物品是在延迟之后才逐个出现的**。所以「匹配上」不是一帧的事，
是一段持续状态：

```
IDLE     OCR 命中 + 网格确认 -> 进入 SESSION
SESSION  每轮做网格 + 色块检测，红品结果 latch
         OCR/网格连续 N 轮失败 -> 结束 SESSION，结算
结算     有红 -> streak 归零；没红 -> streak += 1
```

两个关键细节，都在 `test_track.py` 里有回归用例：

- **红品必须 latch**。搜刮过程中物品逐个出现，红品可能只在某几帧可见
  （随后被别的物品盖住）。不 latch 会漏。
- **结束要去抖**（`--miss-need`，默认 3）。搜刮动画会让网格检测间歇性失败，
  连续 N 轮都失败才算真关了。

输出长这样：

```
[02:41:03] 开箱  保险箱   格子=(4.0, 4.0) 间距=(91, 91)
[02:41:11] 无红  保险箱 (4.0, 4.0)   -> 连续 3 个未出红
[02:42:20] *** 出红 ***  保险箱 (4.0, 4.0)
           连续 7 个保险箱未出红，此处中断
```

退出时打印汇总 + 把完整历史写进 `debug/track_*_history/history.json`。

位置固定的话，只 OCR 那一小块能降到 **~10ms**，整条链路开销掉一个数量级。

## 检测流程

```
整帧 2560x1440
 └─ 第 0 层  只保留右侧 right_frac（默认 0.40）
            左侧 0.6 是背包，里面也可能有红品 → 直接不看，从源头排除干扰
 └─ 第 1 层  边缘密度 → 闭运算 → 连通域，按面积依次试前 6 个
            每个跑：尺寸 / 填充率 / 长宽比
 └─ 第 2 层  在候选内对边缘投影做自相关，再用「折叠一致性」选出真周期
            格子数必须是整数
 └─ 第 3 层  面板内按实测色值做红色掩码 → 连通域 →
            面积占比 / 实心度 / 长宽比 / 核心色值匹配率
 └─ 第 4 层（仅 watch）面板位置连续 3 帧稳定才算数
```

## 路线二：安全箱监控

`select-box` 抓一帧让你拖动鼠标框选安全箱，存成**归一化比例**（换分辨率不用重标）。
`box` 之后只盯那一小块。

### 核心问题：安全箱会累积

第一个摸到的红放进去后就一直在那儿。**不能判断「箱里有没有红」**——那会让之后
每一次开箱都被误判成出红。必须判断「**新增**了红」：

```
基线 N = 首次观察到的红品数
当前数 > N  ->  报告新增，N = 当前数
当前数 < N  ->  箱子被清空 / 换局，N 归零重新基线
其余        ->  静默
```

### 跨局的基线问题（待确认）

安全箱里的东西**跨局是否保留**决定了基线怎么处理：

- **每局清空** → 现在的自动基线就够了
- **跨局保留** → 上一局的红会一直在箱里。但因为逻辑是「只报新增」，
  基线会自动停在旧的数字上，**不会误报**；新摸到的红照样会被检出。
  唯一影响是「减少」事件不会触发，这只是显示问题，不影响功能。

### 数出「摸了几个保险箱」：OCR 容器名字

安全箱只能告诉你**什么时候拿到红**，告诉不了你**摸了几个保险箱**。
而**不能简单地数「搜索面板出现了几次」**——搜的容器不都是保险箱
（工具箱、医疗箱、背包都会弹面板）。

解法是读面板里的**容器名字**，只数目标容器。走 Windows 自带的 OCR：

```bash
python main.py --window 暗区 name        # 打开一个保险箱面板，看 OCR 读出什么
```

`name` 倒计时 5 秒后抓帧，打印右侧区域识别到的**全部文字**（去空白后的形式），
并标出哪行命中了关键词。**先用它确认游戏里那个字到底怎么写**。

#### 为什么不用 PowerShell

Windows OCR 从 PowerShell 调最省事，但本机执行策略是 `Restricted`，
`.ps1` 脚本文件被系统禁止运行——要跑就得加 `-ExecutionPolicy Bypass`，
那是在拆系统的安全开关，不做。改用 WinRT 的 Python 投影包，同一个引擎，
正规入口，没这个问题。

```bash
pip install winrt-runtime winrt-Windows.Media.Ocr \
    winrt-Windows.Graphics.Imaging winrt-Windows.Storage \
    winrt-Windows.Storage.Streams winrt-Windows.Globalization \
    winrt-Windows.Foundation winrt-Windows.Foundation.Collections
```

都有 Python 3.13 的 wheel，不用编译。

#### 两个实测踩到的坑

1. **OCR 会在汉字之间插空格**：`安全箱` 读出来是 `'安 全 箱'`。
   直接 `"安全箱" in text` 是 False。所有文本比较必须先过 `ocr.flatten()`
   去掉空白——`test_ocr.py` 里有专门的回归用例。
2. **OCR 会把形近字读错**：实测「钛金安全箱」被读成「钍金安全箱」
   （钛/钍字形极像）。但这**不影响判定**，因为用的是子串匹配 `安全箱`，
   首字读错照样命中。这正是**必须用子串而不是整串相等**的原因。

#### 实测性能

右侧区域 1024x1440，`upscale=1.0` → **126 ms** 识别 20 行。
放大反而更差：`upscale=1.5` 耗时涨到 225 ms 且质量下降（`烟雾弹` 读成 `烟 的 弹 号`）。
每次开箱只 OCR 一次，这个开销完全可接受。

## 红色判据（关键）

### 红品槽位底色是**半透明**的 —— 色值会漂

这是整整返工一轮才搞清楚的。同一个红品，在三种情况下量到三个色值：

| 场景 | hex | 色相 | S | V | \|G-B\|/max |
|---|---|---|---|---|---|
| 整备界面（暗场景） | `#331410` | **3** | 175 | 51 | 0.20 |
| 对局·未选中 | `#73312A` | **3** | 162 | 115 | 0.14 |
| 对局·选中高亮 | `#9E7B70` | **7** | 74 | 158 | 0.09 |

**色相恒定在 3~7，只有亮度和饱和度在变**（差了三倍）。因为槽位底是半透明的，
压在暗背景上就暗、压在高亮态就发粉。

所以**按单一色值精确匹配是错的方向**——我第一版就是这么做的，拿 `#331410`
标定，结果对局内的红品一个都检不出来。

### 判据：色相 + G≈B

```
色相 <= 9 或 >= 170       红跨 0，所以是两段
S >= 55    V >= 40        排除黑和灰
|G-B| / max(G,B) <= 0.28  红是 R 远大于 G 且 G 与 B 接近
```

`G≈B` 那一条用来把红和金/棕/面板底分开：

| 目标 | hex | 色相 | \|G-B\|/max | 结果 |
|---|---|---|---|---|
| 红品（未选中） | `#73312A` | 3 | 0.14 | **检出** |
| 红品（选中） | `#9E7B70` | 7 | 0.09 | **检出** |
| 红品（暗场景） | `#331410` | 3 | 0.20 | **检出** |
| 金币底 | `#FFFF97` | 30 | 0.41 | 排除 |
| 金棕品 | `#352512` | 16 | 0.51 | 排除 |
| 面板棕底 | `#5B3722` | 11 | 0.38 | 排除 |
| 手表槽底 | `#252624` | 45 | 0.05 | 排除 |

色相 7 vs 11 是最窄的一处，靠 `G≈B` 兜住。

### ⚠️ 容器名字标签的底色也是红的

实测「机密保险箱」标签底色 `#D29285`（色相 **5**）、`#9C4B3F`（色相 **4**）——
和红品**同色系**，颜色分不开。只能靠两件事：

1. **形状**：标签是扁长条（实测 aspect 3.2~3.4），红品是方格（0.7）。
   `red_aspect` 上界 2.8 把它挡掉。
2. **位置**：用 OCR 给出的名字 bbox 往外扩一圈做排除框，
   `track._label_exclude()` 算它。

排除判据用**「色块中心落在标签框内」**，不是「有任何重叠」——
踩过一次：排除框底部只多出 9px 就盖到紧邻的第一个格子，
真红品因为「重叠 7%」被直接丢掉。红品的中心在标签框下方很远，中心判据干净利落。

## 已知限制

1. **单帧 `snap` 无法排除周期性场景纹理**。枪械皮肤上的重复花纹、天花板格栅、
   地砖都会产生假周期。`watch` 用「位置连续稳定」过滤，`snap` 没有这一层。
2. **只在无边框窗口化下可靠**。独占全屏抓不到 / 抓到黑屏。
3. **必须关 HDR**，否则抓到的是错误的 sRGB 值。
4. **换显示器 / 改画面亮度后要重新标定 `red_target_bgr`**。核心匹配率对绝对
   色值敏感，换设备后红品底色会漂移。
5. **抓显示器时 0.6/0.4 无意义**。那种情况下比例是相对显示器而非游戏窗口的，
   只有无边框全屏时才恰好相等。请优先用 `--window`。
6. `red_mode="hsv"` 是给「没有标定色值」的场景留的通用兜底，精度明显不如
   默认的 `ratio` 模式。

- E **右面板只有金品** → `ui_found=True, red_found=False`（防与金/棕品混淆）

D 和 E 用的是**实测色值和实测槽位形态**（红底上叠物品图案和白字，会打洞），
不是纯色方块，所以能真实反映 fill 只有 0.81 的情况。

## 踩过的坑（都已在代码里修掉）

1. **`cv2.imwrite` 在非 ASCII 路径上静默失败**。目录是 `C:\Users\鲁迅\...`，
   必须用 `imgio.imwrite_u`（imencode + Python 文件对象）。
2. **自相关取最大峰会测错周期**。格子间距 90px 的图，在 74px（= 格子宽，

3. **只取最大连通域不够**。角色轮廓会和面板粘成一个脏的大连通域，
